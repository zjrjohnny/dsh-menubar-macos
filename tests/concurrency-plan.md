# Web 与 CLI 共用 DSH_HOME 的并发测试设计

## 当前结论

本仓库不掌握 dsh sessions/storages 的稳定写入 API，也未确认其 JSON、zstd 持久化层具有跨进程锁。因此现有自动测试**不覆盖**真实业务并发，不能据此宣称 Web 与 CLI 共用 `DSH_HOME` 是安全的。

在上游实现或验证锁之前，生产建议是同一 `DSH_HOME` 同时只允许一个写实例。

## 可执行测试的前提

开始前必须从 dsh 上游确认两条可重复、非交互、确实会修改同一业务对象的命令：一条代表 Web 写入，另一条代表 CLI 写入。若只能通过 HTTP API 驱动 Web，也必须固定 API 版本和预期响应。

所有压力测试必须设置全新的临时目录，例如：

```bash
TEST_DSH_HOME="$(mktemp -d "${TMPDIR:-/tmp}/dsh-concurrency.XXXXXX")"
export DSH_HOME="$TEST_DSH_HOME"
```

禁止将 `~/.dsh` 软链到测试目录，也禁止复制包含真实凭据的生产目录作为样本。

## 建议矩阵

1. 先串行运行写入 A、B 各 100 次，记录应产生的对象数、最终字段和文件集合，作为基线。
2. 在干净的临时目录中并行运行 A、B，各 1000 次；随机加入 0–50 ms 抖动。
3. 重复并行测试至少 20 轮，并在写入期间随机向其中一个进程发送 SIGTERM，随后重新启动。
4. 每轮结束后等待所有子进程退出，再执行完整性检查。
5. 比较串行基线与并行结果，区分语法损坏、丢更新、重复记录和最后写入覆盖。

## 每轮完整性检查

- 对所有 JSON 文件执行严格解析，不允许空文件、尾随截断或类型漂移。
- 对所有 zstd 文件执行 `zstd --test`（若格式包含多帧，也要覆盖全部帧）。
- 用 dsh 自身只读命令重新加载全部 sessions/storages，确认它没有静默跳过坏记录。
- 校验业务层唯一 ID、预期对象数量、单调序号和最终字段值。
- 保存失败轮次的目录副本、两个进程的 stdout/stderr、dsh 与 Node 版本。

仅做“最终文件能解析”不够：两个进程都可能成功写出合法文件，但其中一个更新被另一个覆盖。

## 通过标准与修复方向

只有在所有并行与终止注入轮次都没有损坏或丢更新时，才能对被测版本作有限结论。若复现问题，优先在上游写入层采用同目录临时文件、flush/fsync、原子 rename，并在读改写事务外围增加跨进程 advisory lock。菜单栏侧的进程警告只能降低误用概率，不能替代写入层同步。
